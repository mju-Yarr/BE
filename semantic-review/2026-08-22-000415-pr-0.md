# Ensom BE 화면 흐름 계약 확장

이번 변경은 6자리 이메일 인증과 가입 티켓, 온보딩 상태, 오늘 플랜, 캘린더 소스 선택, 경로 상세 영속화, 북마크·최근 목적지를 하나의 화면 흐름 계약으로 연결한다. 동일 signup 엔드포인트가 티켓 없는 레거시 분기를 계속 허용해 새 가입 계약의 필수 검증을 클라이언트가 생략할 수 있다. 새 화면 집계 경로에는 쿼리 증폭이 생겼고, 최근 목적지와 닉네임에는 동시 요청 시 정합성이 깨지는 경합이 남아 있다. 컴파일 재실행과 전체 테스트는 통과했지만 신규 보안·화면 흐름을 직접 검증하는 테스트는 없다.

Watch for: **High — confirmed** 티켓 생략으로 6자리 atomic signup·필수 동의·비밀번호 복잡도 검증을 우회할 수 있음; **High — likely** 공개 send/confirm에 전용 abuse quota가 없어 SMTP 남용과 장기·분산 대입을 막지 못함; **High — confirmed** 닉네임 선조회가 DB 유니크 제약 없이 경쟁함; **High — confirmed** 최근 목적지의 read-then-insert 경합이 일정 트랜잭션까지 롤백함; **High — confirmed** 일반 일정 생성에서 `depart_at`이 계획 계산에 전달되지 않음; **High — confirmed** Event/Today/최근 목적지 화면 API가 N+1 쿼리를 발생시킴; **High — confirmed** 신규 핵심 흐름의 회귀 테스트가 없음.

**Verdict**: NEEDS_CHANGES

## High-level view

`POST /auth/email/signup`은 `verificationTicket` 존재 여부를 서버 정책이 아니라 요청 본문으로 결정한다. **High — confirmed:** 티켓을 빼면 atomic signup 전용 이름·닉네임·timezone·installation ID·필수 동의·비밀번호 복잡도 검증이 모두 건너뛰어지고 기존 링크 인증 가입으로 내려간다.

6자리 코드는 challenge당 5회 실패 후 무효화되고 재발송은 email당 60초 cooldown을 둔다. **High — likely:** 공개 엔드포인트에는 인증 전용 IP·email 누적 quota가 없고 nginx의 공통 30 req/s 제한만 적용되므로, 수신자를 바꾼 대량 메일 발송과 challenge 갱신을 통한 장기 대입이 가능하다.

가입은 닉네임 가용성을 먼저 읽은 뒤 사용자를 저장하지만 V29는 닉네임 유니크 제약을 추가하지 않는다. **High — confirmed:** 동시에 같은 닉네임으로 가입하면 두 요청이 모두 통과해 가용성 API와 저장 상태가 모순될 수 있다.

일정 생성·수정은 최근 목적지를 같은 트랜잭션에서 기록한다. **High — confirmed:** 같은 사용자와 좌표의 동시 요청은 V29의 좌표 유니크 제약에서 하나가 실패하며, 보조 UX 데이터 충돌이 본래 일정 저장까지 취소한다.

새 `anchorMode`는 Event와 응답에는 영속화되지만, 사전 선택 경로가 없는 계획 계산은 여전히 상수 `arrive_by`를 사용한다. **High — confirmed:** `depart_at` 일정이 저장값과 다른 시간 의미로 경로·플랜을 계산한다.

화면 응답 조립은 행마다 별도 repository 조회를 수행한다. **High — confirmed:** 범위 제한이 없는 Event 목록은 이벤트당 최대 두 쿼리, Today Plan은 계획당 여러 상세 쿼리, 최근 목적지는 최대 50개의 bookmark 존재 쿼리를 추가한다.

현재 변경된 테스트는 기존 bootstrap/CORS/AI 설정 기대값만 조정한다. **High — confirmed:** 코드·티켓 replay, atomic signup, PostgreSQL V29, 소유권, 최근 목적지 경합, `depart_at`, Today Plan 쿼리 동작을 검증하는 신규 테스트가 없다.

## 티켓 유무가 결정하는 atomic signup 보안 경계

**High — confirmed.** `AuthService.signup`은 `verificationTicket`이 non-blank일 때만 `validateAtomicSignup`과 `consumeSignupTicket`을 호출한다 (`src/main/java/com/hq/backend/auth/AuthService.java:118-135`). 티켓을 생략하면 `SignupRequest`의 nullable 필드가 허용되고 이름·닉네임·timezone·installation ID와 `terms/privacy/location` 동의가 검증·기록되지 않는다. 복잡도 정규식도 건너뛰며 DTO 최소 길이가 기존 10자에서 8자로 낮아져 영문·숫자 조합이 없는 8자 비밀번호도 허용한다 (`src/main/java/com/hq/backend/auth/dto/SignupRequest.java`, `AuthService.validateAtomicSignup`).

레거시 분기는 이메일 링크 인증 전에는 로그인을 막으므로 즉시 access token을 얻는 우회는 아니다. 그러나 새 계약의 6자리 확인과 필수 동의를 요청 필드 하나로 선택적으로 만들며, 이메일 인증이 비활성화된 환경에서는 `emailVerifiedAt`까지 즉시 설정한다 (`AuthService.signup`, lines 172-174). atomic signup을 현재 계약으로 강제하고, 레거시 호환이 필요하면 별도 API 버전에도 동일한 동의·비밀번호 정책을 적용해야 한다.

## 인증 코드 엔드포인트의 누적 abuse 제한 부재

**High — likely.** `EmailVerificationService.sendCode`는 email별 최신 challenge의 60초 cooldown만 확인하고, `confirmCode`는 challenge별 5회 실패만 센다 (`src/main/java/com/hq/backend/auth/EmailVerificationService.java:57-103`). email을 바꾸면 SMTP 발송을 계속 유발할 수 있고, 한 대상도 매 cooldown마다 새 challenge를 만들어 누적 실패 횟수를 초기화할 수 있다. 저장소에서 확인되는 edge 제한은 모든 API에 공통인 IP당 30 req/s뿐이다 (`nginx/default.conf:1,28`, `nginx/production.conf:1,64`).

실제 배포 앞단의 별도 WAF·메일 사업자 quota를 확인해야 한다. 저장소가 최종 제어 지점이라면 send와 confirm에 별도 IP/email 시간창·일일 상한을 두고, challenge 교체로 상한 상태가 초기화되지 않게 하며 429 응답과 모니터링을 추가해야 한다.

## 닉네임 가용성의 TOCTOU

**High — confirmed.** `AuthService.validateAtomicSignup`은 `userRepository.existsByNickname` 결과만 보고 가입을 진행한다 (`src/main/java/com/hq/backend/auth/AuthService.java:172-175`). V29는 users에 `full_name`과 `registration_installation_id`만 추가하고 (`src/main/resources/db/migration/V29__screen_flow_contracts.sql:4-5`), 기존 migration에도 nickname 유니크 제약이 없다. 두 트랜잭션이 같은 닉네임을 동시에 조회하면 둘 다 저장되어 `/auth/check-nickname`과 `NICKNAME_EXISTS` 계약이 깨진다.

V29에 제품의 비교 규칙과 같은 DB 유니크 인덱스를 추가하고 가입 insert의 제약 위반을 `NICKNAME_EXISTS`로 변환해야 한다. 사전 조회는 UX 힌트로만 남겨야 한다.

## 최근 목적지 충돌이 일정 저장을 취소하는 경합

**High — confirmed.** `RecentDestinationService.record`는 `(userId, lat, lng)`를 조회하고 없으면 insert한다 (`src/main/java/com/hq/backend/bookmark/RecentDestinationService.java:18-34`). V29는 같은 키에 `uq_recent_destination_coordinates`를 두지만 (`src/main/resources/db/migration/V29__screen_flow_contracts.sql:59`), 충돌 재조회나 PostgreSQL upsert가 없다. `EventService.create`와 `update`가 `@Transactional` 상태에서 이를 호출하므로 (`src/main/java/com/hq/backend/event/EventService.java:87,138-139,143,202-203`), 같은 좌표의 동시 일정 요청 중 하나는 commit 시 `DataIntegrityViolationException`으로 일정·플랜 변경 전체가 롤백된다.

`INSERT ... ON CONFLICT (user_id, lat, lng) DO UPDATE`에서 `use_count`와 최신 값을 원자적으로 갱신해야 한다. 일정 트랜잭션과 결합하지 않아도 된다면 보조 데이터 실패가 일정 성공을 취소하지 않는 별도 커밋 경계도 필요하다.

## `depart_at`을 무시하는 일반 계획 생성

**High — confirmed.** Event 생성은 요청의 `anchorMode`를 검증해 저장하고 응답에도 노출한다 (`src/main/java/com/hq/backend/event/EventService.java:89-92`, `src/main/java/com/hq/backend/event/dto/EventResponse.java:48-50`). 그러나 `PlanCreationService.compute`는 사전 선택 경로가 없는 경로에서 provider와 plan engine 양쪽에 상수 `ANCHOR_ARRIVE_BY`를 전달한다 (`src/main/java/com/hq/backend/plan/PlanCreationService.java:172-184`). `SelectedRouteSearch` 경로만 선택 당시 anchor를 전달하므로 동일한 `depart_at` 요청이 route option 선택 여부에 따라 다르게 계산된다.

일반 계산도 `event.getAnchorMode()`를 source of truth로 사용하고 provider 기준 시각과 engine 입력을 함께 맞춰야 한다. 생성·재계산·PATCH 후 응답에서 두 anchor mode의 출발/도착 시각과 plan 경계를 검증해야 한다.

## 홈 화면 조립의 다중 N+1

**High — confirmed.** `EventService.list`는 범위 길이와 결과 수를 제한하지 않은 채 각 event를 `toResponse`로 보내고, event마다 active plan과 선택 route를 조회한다 (`src/main/java/com/hq/backend/event/EventController.java:29-33`, `src/main/java/com/hq/backend/event/EventService.java:55-60,308-314`). 큰 범위는 기본 목록 뒤 최대 `2N` 쿼리를 추가한다.

`TodayPlanService.getToday`도 event마다 active revision, `PlanService.get`, route 조회를 수행한다 (`src/main/java/com/hq/backend/plan/TodayPlanService.java:43-71`). `PlanService.toDetail`은 event, checklist, context, wellness action, wellness score를 각각 조회하며 이 경로는 `BootstrapService.bootstrap`에도 포함된다. `RecentDestinationService.list`는 최대 50개 결과마다 bookmark 존재를 조회하고 (`src/main/java/com/hq/backend/bookmark/RecentDestinationService.java:35-43`), Calendar connection 목록도 connection별 source를 조회한다 (`src/main/java/com/hq/backend/calendar/CalendarService.java:166-175`).

사용자 범위 batch query나 projection으로 응답을 조립하고 Event 목록에 최대 기간 또는 pagination을 적용해야 한다. bootstrap 쿼리 수가 일정 수와 선형 증가하지 않는 검증도 필요하다.

## 보안·정합성 경로를 통과하지 않는 테스트

**High — confirmed.** `src/test` 전체에서 `verification/send`, `verification/confirm`, `verificationTicket`, `RecentDestination`, `TodayPlan`, `Onboarding`, `writeToCalendarSourceId`, `bulk-delete`, `depart_at`을 검증하는 테스트가 검색되지 않았다.

PostgreSQL에서 V29 적용과 Hibernate validate를 실행하고, 코드 실패 횟수 커밋, 동일 코드·ticket의 단일 성공, signup 실패 시 ticket 소비 롤백, calendar source·route option·bookmark 소유권을 검증해야 한다. 동시 닉네임 가입·최근 목적지 기록, 두 anchor mode, Event/Today 쿼리 수도 포함해야 한다.
